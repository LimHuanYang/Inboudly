Token-refresh — failure-path UI

the happy path is silent; these are the states a user sees when refresh fails ui-ux-pro-max

Most of this feature is invisible — the publish worker refreshes an expiring OAuth token before posting, silently. The UI only changes on the failure path: when a token can't be refreshed (revoked / fully expired), the account auto-disconnects. Two surfaces need to communicate that clearly.

The connect row now has three states. "Reconnect needed" must read as distinct from a fresh "Not connected" — the user was connected and it lapsed.

Design notes (ui-ux-pro-max)

  • state-clarity · 3 states Connected / Reconnect-needed / Not-connected are visually distinct: green check, amber-bordered warning card, neutral. "Reconnect needed" reuses the connected row's avatar/identity (the account still exists) but flips to amber — signalling "lapsed," not "never linked."
  • color-not-only Every state carries an icon + text label, never colour alone — "✓ Connected", "⚠ Reconnect needed", "Not connected" — readable for colour-blind users and screen readers.
  • error-clarity The failure states the cause ("access expired") not a generic "Failed", so the user knows it's an auth lapse, not a bug or a bad post.
  • error-recovery Every failure offers the fix inline: the connect row has a primary Reconnect; the failed post has Reconnect & retry + a Settings link + Reschedule. No dead ends.
  • a11y The reconnect-needed badge + the post error use role="alert" / status semantics so screen readers announce the lapse; Reconnect/Retry are real buttons ≥40px with focus rings.
  • consistency Same connect-row layout (icon · identity · status · action) as the existing Instagram/TikTok rows — only the status + action swap. The amber warning token matches the Composer's existing "uses your credits" / advisory cues.
  • silent happy path No UI for the success case — a refresh that works produces zero noise. We only spend the user's attention when action is required (don't over-notify).
