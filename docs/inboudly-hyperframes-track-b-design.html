Track B — branded video, as a second engine.

HyperFrames renders deterministic, on-brand MP4s from HTML templates + your BrandKit. It plugs into Inboudly as one more video provider — everything downstream stays the same.

The map confirmed it: the runner, cron reaper, status lifecycle, polling, R2, MediaAsset, and the whole publish chain are provider-agnostic. HyperFrames = a new provider + a render method. Nothing downstream changes.

What I need your nod on

Recommendations marked. Override any of them.

D1

How to render

Shell out to the CLI recommend

npx hyperframes render --variables '{…}' --output tmp.mp4 per render. Matches the install (the skills are the CLI), process isolation, deterministic, no heavy in-process dep.

@hyperframes/producer in-process

Tighter integration, but bundles Chrome control into the API process + a big dependency. Defer.

D2

Data model

Reuse VideoGeneration recommend

+ two additive fields (templateId, variables Json). Reuses the entire runner / cron / GET /ai/video/:id polling / tray. One tiny migration. provider='hyperframes', no BYOK key (it's free/local).

New TemplateVideoJob table

Cleaner separation, but duplicates the runner + cron + tray + polling. Over-built for v1.

D3

Templates

Not really a fork — the HyperFrames-native way. Bundle 2 composition projects in the API; each declares data-composition-variables and is rendered by injecting --variables:

brand_primary · brand_accent · brand_font · logo_url
caption_en · caption_zh · title · cta · background_url · width · height
